# Field Notes — 2026-10-31

## 1. The Plugin Session Lints Only the Rules and Programs Oxlint Asks For (`i-6r5s`)

- **Profile:** on sudocode (873 files Oxlint lints, 10 tsconfigs, release build), the session's first call took 1.05 s:
  - Program builds took 0.10 s and rules 0.90 s. Of the rule time, the frontend tsconfig took 0.44 s and the files outside every tsconfig 0.23 s.
  - The walk, grouping and finding conversion took 0.02 s together.
  - It ran every catalog rule over every lintable file whatever Oxlint enabled, including `no-vague-names`, the only rule that is off by default.
- **The baseline was not equal work:**
  - Sudocode's frontend tsconfig sets `baseUrl`, which the pinned compiler rejects. So the hook path's helper reports one `tsconfig-error` and lints none of the frontend's 360 files.
  - The session suppresses program diagnostics and lints them.
  - With `OXLINT_TSGOLINT_DANGEROUSLY_SUPPRESS_PROGRAM_DIAGNOSTICS=true` the hook path lints them too and takes 1.27 s, not 0.75 s.
- **Buckets on equal work** (97 default rules, same files, median of 3):

  | Bucket                   | Hook path | Plugin path |
  | ------------------------ | --------- | ----------- |
  | Startup and regular pass | 0.04 s    | 0.07 s      |
  | Program builds           | 0.10 s    | 0.15 s      |
  | Rules                    | 1.08 s    | 1.00 s      |
  | JS handoff               | none      | 0.63 s      |
  | Relayed helper           | none      | 0.10 s      |
  | Total                    | 1.35 s    | 1.93 s      |

  The JS handoff was 0.63 s because Oxlint deserialized and walked every file's AST for the bridge's `Program` visitors.

- **Memory:**
  - The session pass made 41.9M allocations, 6.4 GB in total. It keeps 0.79 GB live afterwards, the programs and checkers the relay serves.
  - Peak RSS was 1.28 GB on the hook path, and 1.76 GB plus a 0.21 GB helper on the plugin path.
- **Per rule:** each rule was run alone; nine of them carry 80% of the solo rule time.

  | Rule                              | Time alone | Allocations | Bytes allocated |
  | --------------------------------- | ---------- | ----------- | --------------- |
  | `no-structural-type-fork`         | 232 ms     | 24.7M       | 1.35 GB         |
  | `no-unsafe-deserialize`           | 204 ms     | 3.0M        | 2.34 GB         |
  | `unknown-input-must-be-decoded`   | 148 ms     | 3.5M        | 0.43 GB         |
  | `no-schema-validator-transcoding` | 147 ms     | 2.0M        | 1.12 GB         |

- **Batches stay per program:**
  - Linting the 873 files one call at a time takes 10.1 s against 1.03 s in program batches, because every call starts 16 checker threads.
  - `no-unsafe-deserialize` finds 196 per file against 192 in batches. Its contextual-type and type-string queries depend on checker history, so batch membership is behavior. _(Correction — disproved same day in section 7 (`i-6kl8`): `no-unsafe-deserialize` produces the exact same 192 findings across 856 single-file headless calls with fresh checkers, batch runs, and the plugin session; the 196 count came from Oxlint's file walk, not checker query history.)_
- **Change:**
  - The bridge reports from `createOnce` `before` hooks that return `false`, so Oxlint builds no AST except for the first file. That file uses a `Program` visitor and reveals the enabled rules.
  - `lintFile` takes the rules the run has enabled so far, and returns only the file's own.
  - The session builds and lints a program's batch on the first request for one of its files, computing only the requested rules and adding later ones to the same batch. The inferred batch builds its family's configured programs first, so its roots keep their old order.
  - A batch is marked linted, and its findings merged, only after its pass returns, so an engine panic surfaces again on the next call as it did on main.
- **Result** (median of 3 on sudocode):

  | Run             | Before | After  | Hook                |
  | --------------- | ------ | ------ | ------------------- |
  | One-rule config | 1.87 s | 0.43 s | 0.81 s (hook-only)  |
  | 97 rules        | 1.99 s | 1.53 s | 1.29 s (equal work) |
  | One server file | 1.22 s | 0.25 s | 0.13 s              |
  - Peak RSS fell from 1.71 GB to 0.72 GB with one rule and from 1.51 GB to 0.37 GB for one file; it is about unchanged with 97 rules.
  - Sorted full diagnostics are identical to main: 12,565 with every rule enabled and 23 with one.

- **Review:** codex `gpt-6.1-sol` and Fable 5.1 found no blocker or high issues.
  - Fable found that a panic during a batch's pass left the batch marked linted, so later calls returned partial findings or a misleading error. Fixed as above.
  - Both found that a rule first seen on a later file, as config overrides cause, adds one pass over each batch already linted. With 98 rules introduced on 98 successive files, the frontend batch took 587 ms against main's 408 ms, about 1.8 ms per extra pass (`i-9jpq`).
  - Fable ran 11 more run shapes against main: overrides that add or remove rules, file subsets, the missing-file path, the inferred slot, the relay with Oxlint's own typed rules, and a repeat run. All matched.
  - A tsconfig that fails to load now fails only the files that need it: files under it and files outside every tsconfig. Files under healthy tsconfigs still lint. On main every call failed. Neither reviewer could make the resolver reject a tsconfig.
- **Remaining gap on equal work (`i-57vj`, now blocking `i-9a21`):** the plugin path still does the hook's rule work, plus a second helper process (0.10 s) and the bridge (0.07 s). A small run lints the whole program of each file it touches.
- **Follow-ups:** the hot rules (`i-15ms`), `no-unsafe-deserialize` depending on batch membership (`i-6kl8`), bridge findings shifted by U+2028, U+2029 or a lone `\r` (`i-5jj1`, reproduced on main), a native smoke of each platform package before publish (`i-45qi`), and the late-override passes (`i-9jpq`).

## 2. `no-structural-type-fork` Indexes Exported Owners Once per Program (`i-15ms`)

- **Cause:** for each candidate type (642 on sudocode), the rule walked every program file (about 1,140), re-derived its test role and origin, and rebuilt the sorted member names of every exported statement.
  - That made 730K candidate-file pairs, about two thirds of its CPU, and 2.5M candidate-statement pairs, about a quarter. The checker comparisons took about 1 ms.
  - It made 24.7M allocations, 59% of the whole every-rule pass.
- **The bar:** a speedup keeps every type-checker query and its order as on main. Checker answers depend on query history (`i-6kl8` — _later disproved in section 7_), so fewer or reordered queries in one rule can move another rule's findings, and matching corpora are evidence, not proof. Bugs may change only as named fixes. Rules whose cost is checker queries wait for `i-6kl8`.
- **Change:** each thread builds an index of exported owners once per program, through one kernel helper (`ProgramFact`) that `ProgramSymbolIndex` now shares.
  - Owners whose members come from syntax are compared from the index.
  - Other exported type aliases still go through the checker on every visit, in main's order, because checker answers depend on query history.
- **Result on sudocode:**
  - From cold checkers, the rule alone adds about 230 ms to a 165 ms pass, against about 1,000 ms before.
  - The every-rule pass makes 21.2M allocations, against 42.2M.
  - End to end with the 97 default rules (median of 5): the hook path went from 1,274 ms to 1,194 ms, and the plugin path from 1,421 ms to 1,311 ms.
- **Proof:** every-rule findings, with messages and spans, are identical to main on homer, sudocode, paseo, t3code and grok-bot (about 46K rows). Codex `gpt-6.1-sol` found nothing at any severity.
- **Measure wins end to end:** a probe that counts allocations through shared atomics overstated this one (2.07 s to 1.28 s), because 16 threads contend on the counters, so time follows allocation count.
- **Fixed alongside:** `lintFile` with an empty rule list now returns no findings. Before, it failed with "was linted but is missing from every program built for it". The plugin never sends an empty list.

## 3. `require-fetch-timeout` Scans for Writes Only When a Binding Leads to `fetch` (`i-15ms`)

- **Cause:** for every call to an imported or locally declared function, the rule walked the whole file for writes to the callee's binding. Only after that did it check whether the binding is a const whose initializer leads to `fetch`, which almost none is.
- **Change:** the cheap check runs first. Both checks are pure syntax, and the rule never asks the type checker anything, so findings and checker history cannot change.
- **Result on sudocode** (medians of 5): the rule alone went from about 250 ms to 143 ms, and the every-rule session pass from 972 ms to 861 ms. Findings are identical, and so are the five corpora.
- **The ranking's floor:** costs from removing one rule at a time carry about 55 ms of run-order bias each. A filename-only rule, `no-debug-residue-filenames`, ranked at 74 ms. Only costs above about 90 ms are real; checker-free rules are better timed alone.

## 4. `symbol_at_node` Resolves Names Only Through the Checker (`i-471h`)

- **Cause:** when the checker bound nothing to an identifier, `antidrift_kernel::provenance::symbol_at_node` listed every symbol in scope and took the first with the same name. On sudocode with the 97 default rules, that ran 14,415 times per pass. 12,118 of those were property names it could not match. Another 706 were property names it bound by name to unrelated declarations: `x.length` to lib.dom's global `length`, `x.status` to `window.status`, and `path.relative(...)` to a local function `relative`. It cost 12.5% of the pass's CPU.
- **Change:** return the checker's symbol, or nothing when the checker returns none or only its unknown placeholder. There is no lookup by name. Joe confirmed that bug fixes may change findings.
- **Blast radius:** 84 call sites in 30 files. Across the five corpora, 13 rows changed, all in `no-wrapping-functions`, and sudocode did not change. Call counts dropped where a wrapper's own `path.relative(...)` or `Buffer.byteLength(...)` call had been counted as a call of the wrapper. Wrappers are newly reported where property reads such as `member.label` or `icon.sha256` had been counted as non-call uses of a local `label` or `sha256`.
- **Review:** codex `gpt-6.1-sol` found nothing at any severity. It confirmed that the removed scope query changed checker state, because it resolves members early, and found no rule whose findings depended on that.
- **Result on sudocode** (medians): the every-rule session pass went from 840 ms to 687 ms, with CPU from 6.0 s to 4.7 s. End to end, the hook path went from 1,152 ms to 933 ms, and the plugin path from 1,292 ms to 1,113 ms, with the same diagnostics.
- **Where the rest of the time goes:** rules take 47% of the pass's CPU, and 30.5 points of that are inside checker queries. The costliest rules each spend 94–99% of their own time in checker queries. Checker-free work is at most about 1.4% of CPU per rule. Wall time also follows program order: programs lint one after another, on 16 checkers for the 257-file server and 6 for the 360-file frontend (`i-2wns`).
- **Work stealing is not shown to change findings:** tsrslint lets an idle checker take another checker's unstarted files, and antidrift leaves that on. In 11 every-rule passes over sudocode and 48 reruns of the chunks behind the `i-20y4` flake, with stealing on and off and on 4 or 32 cores, findings never changed. Turning stealing off doubled those chunks' time.

## 5. Rust Rules Ship as a Catalog Configured from Cargo Metadata (`i-66ch`)

- **Owner:** `[workspace.metadata.antidrift]` in the workspace `Cargo.toml` owns Rust rule levels, crate and module layers and forbidden calls, decoded once with `deny_unknown_fields`. `policy/agent-guardrails.yaml` no longer lists `rust/*` rows; the generator asks the built linter (`rust --list-rules --format json`) and renders the general cluster line and a "Rust house style" section.
- **Deleted from the shipped engine:** `rust/target-manifest-policy`, `rust/require-rule-scope`, `rust/no-duplicate-scope-fields`, `rust/no-discarded-decoded-config`, `antidrift/no-tsrslint-sourcefile-listener` and the hardwired crate order and kernel ranks. A rule without a scope now fails to compile (`ScopedRule`); the SourceFile listener is a configured `rust/no-forbidden-call` row.
- **Measured with shipped defaults** (installed binary, no config): tsrs 447, tsrslint 53, uv 511, biome 1,202, oxc 894, against 55,118 / 1,159 / 38,984 / 122,347 / 146,679 on main where the house-style rules were on. Largest precision moves: orphan modules biome 812 to 7 (raw identifiers, macro-declared directories, generated files), strict serde oxc 305 to 66 (tuple, transparent and flatten containers), silent discard biome 133 to 19 (`Err(_)` arms report only when they mint a new error or an empty value), wrappers biome 67 to 36 (proc-macro, attribute and cfg-gated functions, identity references, public uncalled functions).
- **Still open:** `no-boolean-map` reports memo caches (`FxHashMap<K, bool>` written in a loop); `no-structural-type-fork` reports nominal AST node pairs in oxc (`StaticBlock` / `BlockStatement`); `no-compat-names` reports domain vocabulary (`WheelCompatibility`, `DeprecatedCode`), the same class the TS rule reports; `no-contract-appeasement-projection` still reports a rebuild into an enum variant of another type (uv `resolution.rs:272`).
- **TypeScript unchanged:** every finding on homer, sudocode, paseo, t3code apps and grok-bot is identical to main's binary (958 / 715 / 4,757 / 4,444 / 1,225 rows).

## 6. Rule Scope Moves to the Engine (`i-66ch`, review round 1)

- **Why:** `ScopedRule::scope()` only proved a rule had a field. The decode (71 `RuleScope::from_options` and 10 `decode_scoped` sites), the storage and the gate (74 `in_scope`, 21 `scope.matches`, 5 `admits_authored_source`) all lived in the rules, which is how a rule could decode options, drop them and store `RuleScope::DEFAULT`; main policed that with two name-matched lints.
- **Shape:** one seam in `crates/antidrift-engine/src/rule_plan.rs` (`instantiate_rule`) splits the `files`/`excludeFiles` envelope, compiles `RuleScope`, and wraps the rule in `Scoped` (`crates/antidrift-engine/src/rule_scope.rs`), the single gate. Policies are a column on each family table: 84 `Everywhere`, 8 `AuthoredSource`, 4 `InferredRole`, 2 `TestFilesOnly`. The Rust catalog carries the same column (`AuthoredSource` for the six rules whose TypeScript counterparts skip tests).
- **Deleted:** the `ScopedRule` trait and 91 impls, every `scope` field, every rule-side decode and gate, `ScopedOptions`/`decode_scoped`/`in_scope`, and the kernel's glob code (kernel `rule_scope.rs` is now `rule_options.rs`: `EmptyVisitor`, `decode_rule_options`, `require_non_empty`, `reject_unknown_options`). Net: 2,574 lines deleted, 994 added across 119 files.
- **Structural proof:** `antidrift-rules` does not depend on `antidrift-engine`, so `use antidrift_engine::rule_scope::RuleScope` in a rule is E0433 and `rust/no-layer-violation` reports it from `layers.crates`.
- **Behavior moves to say in the report:** `no-pass-through-parameters`, `no-wrapping-functions` and `no-contract-appeasement-projection` moved from "skip generated" to `AuthoredSource` (also skips test roles and declaration files) _(Correction: `62ab10b` restored `ScopePolicy::ExceptGenerated` for `no-pass-through-parameters`, `no-wrapping-functions`, and `no-contract-appeasement-projection` so test and declaration files are not silently skipped)_; `no-placeholder-tests` now admits the headless placeholder file names like `no-repo-state-mirror-assertion` did; `docs-source-policy` keeps its policy-file predicate in the rule (it is an option, not a scope policy); `no-host-path-literal` is a fourth `InferredRole` site.

## 7. Precision Lane: Compat Names, Enum Twins, Rule Options, Hook Path (`precision-and-options`)

- **`no-compat-names` tokens (`i-1880`):** across homer, sudocode, paseo, t3code, grok-bot and the five Rust corpora every `retire*` name was a product action and every `compatibility`/`incompatibility` name a domain noun, so both leave the token list. A sibling gate (report only when the plain name is declared) was built and measured first; it dropped true positives (sudocode `migrateFromLegacy`, `LegacyShimExecutorWrapper`; paseo `migrateLegacyImages`), so the gate is gone and the sibling is only named in the message, resolved program-wide through the kernel `DeclaredNameIndex` (TypeScript) and crate-wide through `CrateNames` (Rust). Lost rows vs 0.21.0: TypeScript homer 7, paseo 46, t3code 53, grok-bot 35, all retire/compatibility; Rust uv 26, biome 4, oxc 1, tsrs 12, same classes. No `legacy`, `deprecated` or `compat` row moved.
- **`rust/no-structural-type-fork` enum twins (`i-m3zl`):** two same-shaped structs that are payloads of two different variants of one enum are nominal by design (the first cut accepted any two payload types of one enum, so two fields of one variant qualified; the codex astra review caught it and the smoke now has that control) (oxc `StaticBlock`/`BlockStatement`, uv per-subcommand arg structs); the struct index records enum payload types and skips the pair. Lost rows: oxc 24, uv 2, all enum twins.
- **Rule options (`i-243g`):** the plugin forwards `context.options` as JSON; the session keys a rule by `name + options JSON`, instantiates each distinct identity once and re-lints a file when a rule arrives with different options. Bridge smoke: `react-max-component-props` with `max: 2` reports a three-prop component, the bare level does not, and `{ maximum: 2 }` fails naming the field.
- **`max-module-lines` warns at 1,000 (`i-4e0g`):** files entering the warn band: homer 4, paseo 38, sudocode 14, t3code 43, grok-bot 7.
- **`i-6kl8` does not reproduce:** `no-unsafe-deserialize` on sudocode gives the same 192 rows from 856 single-file headless relay calls (fresh checkers each), one batch run twice, the plugin session, and the pre-batching session at `74bd54c^`; the 196 counted during `i-6r5s` came from Oxlint's file walk, not checker history.
- **Hook path and session disagree on a rejected tsconfig (`i-4vsx`):** sudocode's `frontend/tsconfig.json` sets `baseUrl`, which tsrs rejects; the headless hook path reports `tsconfig-error` per file and lints none of them (164 rows), the session suppresses program diagnostics and lints them (192). One owner is still needed.
- **Generated hooks pointed at `src/` (`i-6v1d`):** the published package ships `dist/` only, but `antidrift generate` wrote `node node_modules/@joedeleeuw/antidrift/src/policy/hooks/<name>.mjs` into `.claude/settings.json` and `.codex/hooks.json`, so every consumer's PreToolUse hook failed with MODULE_NOT_FOUND; it only worked here because `node_modules` links `tooling/antidrift`. The hook now runs as `pnpm exec antidrift hook <name>` from a hook table in the CLI, and the packed consumer smoke runs `antidrift generate` and executes the generated command (exit 2 on a protected file, 0 under `[policy-change]`). Found by the codex astra directional review.
