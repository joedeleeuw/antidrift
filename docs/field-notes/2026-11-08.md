# Boundary rule follow-ups

Resolved in 0.28.2: imported schema `.or(z.unknown())` provenance, nested object array element proofs, element-preserving refinements, duplicate typed diagnostics, local nongeneric unknown return aliases and PromiseLike, and synchronous/asynchronous container consistency. Field proofs stop at spreads or computed keys that can overwrite the selected field. Runtime compatibility vocabulary is allowed while backward compatibility and compatibility shim/fallback/layer names remain findings.

Independent review caught an unsafe spread proof and an overbroad compatibility exemption; both reproductions now pass in ESLint and Oxlint. Proposed JSX-child and entity-writeback exemptions were retracted because their evidence did not establish the intended invariant. Homer's JSX finding instead exposed duplicated safe-area padding ownership, fixed in the consumer.

Remaining confirmed coverage gaps from review:

- Unknown declarator/assertion checks disagree with returns for local aliases and unknown unions (`boundary-schema.js`).
- Alias resolution should select type-alias declarations from all binding definitions and bound recursion depth. Generic, imported, qualified and Awaited aliases need typed-host resolution before expanding portable syntax heuristics.
- Aliased opaque schema branches and imported receivers without a Schema suffix are not always recognized on untyped hosts.
- Element mutation after decoding needs a separate ownership proof; current syntactic matching does not establish immutability.
- Provenance traversal performance has not been measured; do not claim a regression or optimization without a profile.
- Homer generation findings exposed competing execution fields and client writes overwriting service-owned outcomes. Homer now retains one service snapshot and restricts clients to insert-once creation and an ID-only preparation-failure command. Keep the entity rule active; an arbitrary patch/replace method name is not proof of canonical ownership.

Proof includes real ESLint/Oxlint counterexamples, typed checks and the packed-consumer smoke. No rule was disabled. A directory name, Promise<unknown> annotation, JSX child or write-shaped call does not by itself establish ownership.

The discarded-decode rule counted raw reads in unreachable sibling switch cases after a terminating case. The correction excludes only sibling cases of the same switch when the decode case ends in an unconditional return, throw, break or continue and the switch is outside loops. Reads in the same case, real fallthrough, conditional returns, reads after the switch and finalizers remain findings. Sixteen baseline/corrected runtime probes agree in ESLint and Oxlint; the full 83-rule and packed-consumer gate passes. Independent review caught loop re-entry in the initial exemption. The fix conservatively retains findings for every switch inside a loop, including break, continue and finally-continue paths. Kimi independently reviewed the corrected rule and found no P0/P1 source defects. Released in 0.28.3.

## JSX forwarding ownership

The pass-through rule now checks that a JSX root is returned by the function
owning the forwarded parameter. A leaf returned inside a map callback is not
the outer component's root. Roots composing child content are also distinguished
from wrappers that only relay parameters or children.

Actual ESLint and Oxlint probes retain plain, conditional, state-only and
children-relay findings while accepting owned content and nested/map composition.
The full check passes all 83 rules, typed ESLint and the packed consumer. A fresh
AST-only scan of 37 audited Homer TSX files decreases from 86 reports to 27;
this is not a typed suppression count. Independent Opus review found no P0/P1.

Non-blocking review follow-ups: root JSX returned through a local const is no
longer traced (`parameter-bag-checks.js:330`); empty fragments and undefined
children are incorrectly considered content (`:343`); stacked TS expression
wrappers can stop the root walk early (`:326`). The existing key-attribute
finding is also inaccurate because React does not pass key to the child (`:368`).
These remain detector coverage/precision limitations; this change does not
claim the entire pass-through audit is resolved.
