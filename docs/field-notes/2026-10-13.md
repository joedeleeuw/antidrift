## Shape-rule review fixes

The G23 review of the combined shape rules held landing on three findings, and the owner set the fixes. The shared matcher now walks every type reachable from both sides and rejects any or unresolved error types. That includes types behind a shared named type and generic references. TypeScript default-library types are compared through their type arguments only, because their own members contain any, for example `thisArg?: any` on Array. The generated-owner skip accepts only a comment that declares the file generated: `@generated`, a `Code generated ... DO NOT EDIT.` line, or a line that opens with "This file was generated by" or "Generated by". A bare "do not edit" does not count.

A missing dependency is reported where the code uses it, on each import, export, require, dynamic import and import-type specifier, as TypeScript reports unresolved modules. A missing dependency that the package never imports is reported once per package at line 1 of the path-sorted first TypeScript source file of that package. A declared package that is absent from node_modules but resolved by the compiler options counts as found. The augmentation exemption is bound to the owner export the interface merges with. An export that only the linted package declares, such as an interface a module augmentation adds, is not an owner. Samples are now labelled from the checker-resolved owner declaration with its complete members.

The nested any/error rejection removes 240 inline reports and adds none. Fresh samples score 23/24 for the inline rule and 17/24 for the dependency rule, with coincidental library matches counted false. Vendored declaration copies, a generated types file without a leading declaration and data-migration snapshots stay visible as dependency false positives. Both rules stay at error. ## Shape-rule review fixes, second round

The second G23 review held landing on dependency coverage and nested unchecked types. A missing dependency is a manifest fact. The preset now parses `package.json` with `@eslint/json` 0.14.0, the release built on the same `@eslint/core` line as ESLint 9.39, and the rule reports a missing package on its key. Import-site reports stay. The deciding fact for an installed package with a dangling types target is where its manifest really lives. A real path under node_modules is an immutable registry artifact that publishes no owners at that subpath, so its key is silent and only an import of it is reported. A workspace or linked package, whose real path lies outside node_modules, is reported on its key, because its declarations exist in source but are unbuilt. effect@3.22.1's `./.index` types entry is a dangling published entry with no owners. Its key in tooling/antidrift/package.json is not reported, and nothing was suppressed.

The identity walk now follows every member and signature type of default-library types with a visited set per type and polarity. Any counts where a value reaches the holder, so `Function`, `JSON`, `Promise` and `RegExp` are rejected and `Date`, `Array`, `Map` and `Set` match. Members of a library or tuple type the holder supplies are runtime-implemented and are not walked. `@generated` counts only as a tag at the start of a comment line. Fresh samples score 22/24 for the inline rule and 14/24 for the dependency rule with coincidences counted false. The dependency rule is therefore under-proven and default-off.
