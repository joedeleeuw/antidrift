## Ideal-form rule usefulness and inferred type ownership

- Reviewed all 99 enabled custom rules against their intended job and actual metadata/source, not only their current detector coverage. Ideal-form judgment: 51 broadly useful, 27 conditionally useful, 18 worth merging, 2 better delegated, and 1 not useful as a deterministic blocking rule (`no-tutorial-comments`). These are product judgments, not maturity metadata, external adoption claims, or assertions that every current implementation is corpus-validated.
- `no-structural-type-fork` is intended to stop a handwritten type from becoming a second, independently drifting definition of a contract with an owner. Ownership need not always be declared: `no-restated-dependency-type` already infers candidates from declared dependencies and public exports, Convex has conventional generated owners, and contextual analysis can prove owner use. Only exact shape equality cannot establish authority by itself.
- Ran current `cloudflare/agents` at `321814b6c13f72cff82161e7eb20312574ac9b7a` and `pingdotgg/t3code` at `71df573f2d6910048e304282b960981cb45672b1` with locked dependencies on Node 24. Cloudflare core checked 860 local object types with zero exact matches against declared, imported package owners; t3code contracts checked 57 with zero exact matches. These are clean controls for this exact detector, not whole-repository cleanliness claims.
- Actual `no-restated-dependency-type` on t3code `apps/server` produced 20 rule findings across 1,228 files in 18 seconds without an ownership registry. Some are genuine duplicated contracts; others are provider-neutral abstractions or frozen migration formats. For example, `DeviceHostReady.run` returns the same three fields as provider-specific `CommandResult` and `OpenCodeCommandResult`, while `legacyThreadPullRequestKey.ts` explicitly says its frozen migration types must not follow live owners. Those are not safe automatic imports.
- Scoped production provenance analysis did prove a registry-free owner relationship in `GitManager.ts:496`: the provider-owned `CommitMessageGenerationResult` flows into the inline `{ subject, body, branch }` parameter. Similar scoped checks for `DeviceToolOpenInput`, the DeviceHost result shapes, `SourceControlAuthProbeInput`, `ProviderAdapterV2OpenSessionInput`, and migration shapes returned no contextual proof. `ThirdPartyLicenseEntry` is duplicated exactly in `scripts/lib/third-party-licenses.ts` and `packages/shared/src/thirdPartyLicenses.ts` without a value-flow witness, so matching exported names and dependency evidence can add authority where local value flow is absent.
- The ideal structural implementation should unify structural/restated/canonical checks and use graduated evidence: package/workspace manifests and public exports, conventional generated owners, matching exported names, exact checker shape, and actual value flow. Shape-only or multiple-owner ambiguity should remain inventory rather than a blocking import recommendation. Explicit registries can resolve genuine ambiguity but are not a prerequisite for useful analysis.
- Unbounded installed-owner and whole-program provenance sweeps were not viable: broad runs took several minutes and one candidate-reduced run exhausted the default heap in the whole-program walk. Exact-shape indexing and finding-file dependency scopes completed the probes. These were research-probe failures, not claims of a production-rule OOM; they show why the ideal implementation must bound candidate and file-graph analysis.
