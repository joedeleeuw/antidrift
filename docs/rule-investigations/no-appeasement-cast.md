# no-appeasement-cast Investigation

## Current Rule

`antidrift/no-appeasement-cast` is exported and enabled at `error` in the typed ESLint configuration. Its registry status is `ready`, with `stable: false`.

The rule is type-aware and derives its decision from `CAST_DECISION_TABLE` in `tooling/antidrift/src/semantic-adapters/cast-proof.mjs`:

1. `double_cast_chain` (`clear`): Inline `as unknown as T` and `as any as T` chains belong exclusively to `no-unsafe-cast-chain`.
2. `type_predicate_implementation` (`clear`): Casts inside the body of a user-defined type predicate (`x is T`) or assertion function (`asserts x is T`) implement the narrowing boundary.
3. `unnamed_target_contract` (`clear`): Targets that are not named `TSTypeReference` contracts are cleared.
4. `non_broad_source` (`clear`): Resolved source types that are neither `any` nor `unknown` are cleared.
5. `untyped_or_empty_target` (`clear`): Resolved targets without at least one `ts.TypeFlags.Object` constituent declaring properties, or branded with the antidrift brand marker, are cleared.
6. `dominating_runtime_proof` (`clear`): Casts proved by a dominating runtime check in the same control flow (`instanceof`, `Array.isArray`, user-defined type predicates, `asserts` calls, `expect(x).toBeInstanceOf(C)`, non-null assertions when only nullishness prevents assignability, or schema decoders) are cleared.
7. `unresolved_type_analysis` (`incomplete`): When TypeScript cannot resolve the source or target type (`errorType`), the rule reports `Incomplete analysis: TypeScript could not resolve the types for this cast.` instead of silently dropping or keeping the hit.
8. `broad_source_to_named_contract` (`report`): All remaining casts from `any` or `unknown` into a named object contract are reported.

Files that declare themselves generated in their leading comment (`@generated`, `Code generated ... DO NOT EDIT.`, `This file was generated by`, or `Generated by`) are skipped. Test files receive no exemption: a cast of test output is reported unless an earlier assertion in the same flow proves the target type checker-visibly.

## Ecosystem Check

Closest supported rule:

- `@typescript-eslint/no-unsafe-type-assertion`

That upstream rule is real and high support. It catches some of the same bad assertions, but it is broader than the antidrift rule. In Chaski, the upstream rule also reports typed SDK/API conversion patterns that this package currently treats as clean controls because their source value is already typed. So the ecosystem rule is not an equivalent replacement for this project scope.

## False-Positive Risks

- Generic API wrappers that return `response.data as T` can be intentional boundary abstractions. The current rule must avoid turning every generic API client into noise unless the source is broad and the target is a named object contract used to silence missing validation.
- SDK conversion methods may produce values whose public type is narrower than the method signature. These need real clean controls before tightening.
- Named array aliases or collection contracts may resolve to non-empty object-like targets and need real-corpus classification before broad claims.
- Angle-bracket assertions and source laundering through intermediate typed variables are known false negatives under the current single-expression proof.

## False-Negative Risks

- If a broad value is first assigned to a precise local type and then cast later, the rule may miss the original laundering site.
- Angle-bracket assertions such as `<User>value` are not visited by this v1 rule.
- A bad cast hidden behind a generic helper can appear as a typed source at the assertion site.
