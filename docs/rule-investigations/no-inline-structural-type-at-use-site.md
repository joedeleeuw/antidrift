# no-inline-structural-type-at-use-site

Reuse an existing object type instead of repeating its properties in a boundary parameter.

The rule checks parameters of exported functions, public methods of exported classes, and methods of exported or returned objects. Component props and callback type declarations remain outside scope.

A matching type must be identical at every depth: the same property names, optional, readonly and visibility flags, index signatures and call signatures. The comparison follows four rules, without exceptions:

1. If either side being compared is the compiler's error type, the comparison is undecided. The rule reports the site as incomplete analysis (`undecided`), never as a silent non-match.
2. If either side being compared is `any`, the types do not match, so `any` never makes two different shapes compare equal.
3. The same type matches, and so do two instantiations of the same generic reference or alias whose type arguments compare equal under these rules. An `any` inside a shared named type is not compared, so it is not a wildcard.
4. Otherwise members, index signatures, and call and construct signatures, including type-parameter constraints and defaults, are compared structurally under the same rules.

Separately written `{ payload: any }` fields, `Promise<any>` or `<T = any>() => T` signatures therefore do not match, while two owners that share a named type containing `any` do, and owners holding `Array`, `Date`, `Map`, `Set`, `Promise` or `RegExp` match like any other named type. This follows the owner's recorded intent that error and any types never match; an earlier reading that rejected any reachable at every depth was a drift from it.

The matcher is `tooling/antidrift/src/semantic-adapters/shape-identity.mjs`, shared with `no-restated-dependency-type`. The inline type needs at least three members. The rule also reports a repeated inline shape within one package. The message names the existing declaration and its repository-relative file and line.

The rule searches source files in the TypeScript program. The search excludes node_modules, TypeScript library files, declaration files whose output paths TypeScript maps from sources in the program, and files whose leading comment declares them generated: a line that opens with an `@generated` tag, a `Code generated ... DO NOT EDIT.` line, or a line that opens with "This file was generated by", "This is generated from" or "Generated by", followed by its source. A bare "do not edit", or `@generated` mentioned in prose, does not count. A package is the nearest directory with a package.json file. An owner derived from the reported declaration is never suggested: when the checker resolves any identifier in the owner's declaration, or in a type alias or interface it references transitively, or in the declared type, or failing that the initializer, of a variable it references (so `const operationAlias = operate` is followed), to a declaration other than a whole module that contains the reported type; function bodies are not followed, because they do not determine a declared type, to a declaration that contains the reported type, as with `Parameters<typeof sync>[0]`, `ReturnType<typeof sync>` or an indexed access on them, that owner is skipped. File names play no part.

The rule requires TypeScript parser services. Missing services produce an error.
